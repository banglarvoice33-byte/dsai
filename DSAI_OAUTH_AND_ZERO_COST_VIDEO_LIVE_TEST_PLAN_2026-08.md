# DSAI OAuth Resolution and Lawful Zero-Cost Video Live-Test Plan

**Status:** Prepared for controlled testing; real provider callback and revoke remain operator-gated.

## 1. What the current blocked result means

The DSAI OAuth harness is intentionally fail-closed. The screenshots show authenticated access to the test harness and recorded `state_mismatch` blocked scenarios, but they do not show a real provider authorization, token exchange, or token revocation. The no-grant credential checks pass for the configured Google and HubSpot sandbox variables, which proves that the variables are structurally present and that the validation request is bounded. It does not prove that the provider console has the exact redirect URI, scopes, consent screen, test user, or production origin configured.

## 2. OAuth resolution sequence

| Step | Operator action | Evidence required | Stop condition |
|---|---|---|---|
| 1 | Confirm the exact HTTPS callback URL for each provider in its developer console | Provider console screenshot or exported configuration, with secrets redacted | Any origin, path, or trailing-slash mismatch |
| 2 | Confirm the same redirect URI is present in the DSAI environment | Variable-presence check, never the secret value | Missing or non-HTTPS redirect URI |
| 3 | Confirm only read-only scopes are enabled for the pilot | Scope list and least-privilege review | Any create, update, send, delete, invite, or export scope |
| 4 | Add the sandbox account as an allowed test user | Provider test-user evidence | Provider blocks unverified test account |
| 5 | Start authorization from the DSAI pilot | Correlation ID and redacted callback metadata | State, PKCE verifier, issuer, or redirect mismatch |
| 6 | Record callback success without persisting raw tokens in the audit view | Authenticated audit record with token metadata redacted | Token or authorization code appears in logs/UI |
| 7 | Revoke the sandbox token using the provider-approved flow | Revocation status and timestamp | Revocation endpoint is absent, ambiguous, or fails |
| 8 | Verify post-revoke access is denied | A denied read-only request or provider error consistent with revocation | Any access remains after confirmed revoke |

No password, OTP, access token, refresh token, or client secret should be entered into chat. Secrets belong in the project secret manager or provider configuration, and the operator should use browser takeover for consent screens.

## 3. Lawful zero-cost video live-test architecture

“Zero-cost” means no additional paid provider charge for a bounded preview, not unlimited generation and not bypassing provider quotas. The live test should begin with a 3–5 second low-resolution preview, one active job per user, a hard daily preview budget, deterministic cache reuse for identical normalized briefs, and a visible queue state. The preview must carry provenance metadata, an explicit provider/model label, content-safety result, estimated compute cost, and a notice that it is a preview rather than a production render.

The cost-control policy should use the following order: cache hit first; local deterministic storyboard/animatic fallback second; an authorized free-tier provider adapter third; and a paid or self-hosted render only after explicit entitlement and consent. A failed job must not silently retry indefinitely. Retry counts, prompt hashes, input-asset hashes, provider response class, and elapsed time may be stored as privacy-safe evidence, but raw prompts, source files, access tokens, and private media bytes must not be copied into telemetry.

## 4. Live test acceptance criteria

A test is accepted only when the preview is generated by an actually configured adapter, the output is linked to a provenance record, the safety and rights gates pass, the quota ledger decrements exactly once, duplicate requests reuse the cache key, cancellation is reversible, and deletion removes the stored media reference according to the retention policy. If no provider adapter is configured, the system must show `provider-gated` or `preview-only`; it must not show `generated successfully`.

## 5. Required operator inputs

The remaining inputs are the provider-specific callback allowlists, a sandbox test account, and permission to complete consent and revoke in the browser. A custom-domain reverse proxy configuration is separately required to eliminate the managed-domain `/healthz` edge discrepancy. No additional credentials are required in chat.

## Release decision

The current state is suitable for a controlled, provider-free preview demonstration and authenticated mock/blocked OAuth audit. It is not yet a full real-provider production pilot until callback, consent, revoke, post-revoke denial, and authenticated performance evidence are recorded.
